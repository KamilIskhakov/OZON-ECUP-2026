## 2. Данные и память

```text
data_start/train.parquet     30 631 006 строк, 180 MB на диске
data_start/sample_submit.csv 250 000 строк
```

Панель приводится к компактным типам **один раз** и кешируется в
`data_work/train_compact.parquet`:

| | Память |
| :--- | ---: |
| Исходник в `Int64`/`Float64` | 4090 MB |
| После даункаста | **1139 MB** |

Ключевое решение: дата заменяется целочисленным индексом дня
$d = (\text{event\_date} - \text{2025-01-01}).\text{days} \in [0, 408]$, тип `Int16`.
Все оконные условия становятся сравнением целых вместо арифметики дат.

**Бюджет памяти** (машина разработки: 18 GB RAM, 11 ядер, без GPU):

| Что | Объём |
| :--- | ---: |
| Панель | 1.1 GB |
| Таблица признаков одного якоря (~200k × 183) | ~290 MB |
| Матрица обучения 4 якоря × 183 признака `float32` | ~600 MB |
| Пик при обучении | 5–6 GB |

> **Главная ловушка проекта.** Три раза подряд процесс падал молча (segfault,
> пустой лог) из-за кеширования признаков для всех комбинаций «якорь × глубина
> окна» сразу: 3 окна × 7 якорей ≈ 6 GB сверх панели. Лечение всегда одно —
> внешний цикл по тяжёлому измерению и явное освобождение внутри. При
> экспериментах с несколькими глубинами окна стройте таблицы **по одному окну**.

Отдельная ловушка: `conda run` буферизует stdout и не пробрасывает stdin.
Для длинных фоновых прогонов используйте прямой путь к интерпретатору с `-u`:

```bash
PY=$(conda run -n ecup which python)
PYTHONPATH=src nohup $PY -u script.py > run.log 2>&1 &
```

## 3. Быстрый старт

```python
import sys; sys.path.insert(0, "src")
from ecup import load_panel, run_validation, make_submission, SplitConfig

df = load_panel()                                  # ~30 с впервые, затем мгновенно
```

## 4. Конфигурация

### `SplitConfig` — нарезка истории

| Параметр | Значение | Комментарий |
| :--- | :--- | :--- |
| `max_history` | 300 | глубина окна признаков; проверено 60…365 |
| `stride` | 30 | шаг якорей; равен горизонту, чтобы таргет-окна не пересекались |
| `n_train_anchors` | 4–7 | больше данных улучшает форму, портит уровень |
| `apply_selection` | `True` | правило отбора на каждом якоре |
| `with_state` | `True` | EWMA, байесовские фильтры, ритм покупок |
| `allow_partial_history` | `True` | ранние якоря с усечённым окном; глубина видна модели |

Глубина окна и число якорей конкурируют за 409 дней истории. При строгом
требовании полной истории и `max_history=365` обучающих якорей не остаётся вовсе.

### `ModelConfig` — гиперпараметры

```python
clf_params = reg_params = dict(
    learning_rate=0.05, num_leaves=63, min_child_samples=200,
    feature_fraction=0.8, bagging_fraction=0.8, bagging_freq=1,
    lambda_l2=5.0, n_estimators=600, verbose=-1, n_jobs=-1)
early_stopping_rounds = 100     # число деревьев подбирается, а не фиксируется
eval_frac = 0.12                # отложенная доля для ранней остановки
refit_full = False              # True для финального сабмита
```

Ёмкость проверена в диапазоне 63…511 листьев и на качество почти не влияет
(разброс 0.0012). Всё решает **число деревьев**: оптимум около 194/197 против
фиксированных 600, то есть модель была переобучена.

## 5. Что происходит при обучении

```text
load_panel()                        панель с индексом дня d
      │
      ▼
selected_users(T)                   правило отбора: событие в каждом из трёх
      │                             последних 30-дневных блоков
      ▼
build_features(T, max_history)      ~116 оконных признаков
      │
      ├── state_features(T)         + 70: EWMA, байесовские фильтры, ритм
      ▼
build_training_set(anchors)         склейка якорей, уровни ℓ и ℓ⁺ каждого
      │
      ├── anchor_weights()          вес 2^(-возраст/90)
      ├── anchor_offsets()          init_score = logit p̄(T), офсет ℓ⁺(T)
      ▼
HurdleGBDT.fit()                    классификатор + регрессия на позитивах,
      │                             ранняя остановка, дообучение на 100 %
      ▼
predict(p_target, m_offset)         ẑ = exp(p·m) − 1
```

Инвариант, который нельзя нарушать: в признаки якоря $T$ попадают только дни
$d \le T$. Окна признаков соседних якорей перекрываются, таргет-окна — нет.

## 7. Сборка сабмита

```python
make_submission(
    split=SplitConfig(max_history=300, n_train_anchors=6, with_state=True),
    a_p=0.0,        # экстенсивная маржа: сезонность туда не идёт
    a_m=0.18,       # интенсивная: ℓ⁺ + a_m
    out_name="submission.csv")
```

Проверки, которые делает функция автоматически: состав и **порядок** `user_id`
берутся из `sample_submit.csv`, пропуски заполняются нулём, отрицательные
клипаются, высота результата сверяется с 250 000.

Ансамблирование делается строго в $z$-пространстве:

$$\hat z_{\text{ens}} = \frac{1}{N}\sum_k \hat z_k, \qquad \hat y = e^{\hat z} - 1$$

При смешивании моделей разных типов приводите уровень смеси к уровню опорного
сабмита: `direct`-модели систематически ниже `hurdle` по среднему $\log(1+y)$,
и без выравнивания в одном сабмите смешиваются два изменения.

## 8. Диагностика

```python
res = run_validation(df=df, split=split, keep_model=True)
res.diagnostics["shape"]     # std остатка — чинится только моделью
res.diagnostics["bias"]      # среднее остатка — чинится одним числом
res.model.best_iters         # сколько деревьев реально понадобилось
res.model.importances(20)    # важность по gain, отдельно для двух голов
```

**Отбирайте конфигурации по `shape`, не по RMSLE.** Валидационный `bias` —
артефакт устройства холдаута: там самый свежий обучающий якорь декабрьский,
и его уровень подставляется январскому окну. При реальном прогнозе уровень
непосредственно предшествующего окна известен точно.

Разрешение валидации: эффекты меньше **0.0005** по `shape` она не различает.

## 9. Структура модуля

| Файл | Содержимое |
| :--- | :--- |
| `config.py` | константы задачи, `SplitConfig`, `ModelConfig` |
| `data.py` | загрузка и даункаст, `selected_users`, `make_target` |
| `features.py` | ~116 оконных признаков, `anchor_relative` |
| `state.py` | EWMA, байесовские фильтры, ритм покупок, фантомные дни |
| `metrics.py` | RMSLE, склейка, поправка prior, `level_shift_cost` |
| `model.py` | `HurdleGBDT`, `DirectGBDT`, `MetricAlignedGBDT` |
| `catboost_model.py` | `HurdleCatBoost` — тот же API и та же семантика офсетов |
| `dataset.py` | многооконная сборка, веса и офсеты якорей |
| `pipeline.py` | валидация, свипы, сабмит |
| `stacking.py` | веса на симплексе, изотоническая калибровка |
| `similarity.py` | эмбеддинги траекторий (измеренный ноль) |
| `sequence.py` | TCN/GRU с attention и multi-task головами |

Последние два оставлены как задокументированные отрицательные результаты —
см. [EXPERIMENTS.md](EXPERIMENTS.md).
